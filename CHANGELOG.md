## [Unreleased]

### Fixed
- The PDP's generated AuthZen TLS keypair was not ignored by git. `.gitignore` still named `services/pdp-service/certs/`, the path the service had before it became `openftv-pdp`, so anyone who ran the demo had a private key staged as an untracked file waiting to be committed.
- **The wallet-disclosed BSN reached the decision log for the akte-van-overlijden flow.** The request-mapper matched `flow == "eudi:attestation"` for equality, but the flow string also carries the bronprofiel (`eudi:attestation:brp`), so the BRP flow fell through to the consent branch: the BSN was never pseudonymised, went to the consent-register as a query parameter, and stayed in `resource.variables` — which the OPA decision log records and Promtail ships to Loki. The same equality check in `engine.rego`'s flow dispatch silenced `EUD0002` entirely, so the flow also denied with `NO_APPLICABLE_RULE` on a query the rule was written to cover. Both now match the `eudi:` family by prefix, covered by a mapper test that asserts no BSN occurs anywhere in the resulting PARC and by policy tests on the dispatch.
- Release workflow builds the `openftv-pdp` image with the repo root as build context, the way compose already did. Its Dockerfile bakes in `./policies` and reads `services/openftv-pdp/mapper`, both of which sit outside the service directory, so the service-scoped context failed on `"/policies": not found` and the image was not published for `v0.5.2`.

### Added
- **OpenFTV Manager: policy distribution as bundles (`make demo-manager`).** The PAP+PIP half of OpenFTV now runs alongside the PDP. It owns the policies in its own Postgres, bundles everything tagged `gbo-authz`, and ships it to each PDP named in `services/openftv-manager/bundles/`; the PDP pulls the bundle at boot (`PDP_BUNDLE_MANAGER`) and receives pushes afterwards, holding no policy files of its own. This is what lets a source-holder change a rule without rebuilding a PDP image. Opt-in via the `manager` profile — without `GBO_BUNDLE_MANAGER` the PDP skips bundle retrieval entirely and keeps loading `policies/` from disk with hot-reload, which is the better loop while writing Rego. The Manager needs no patch, unlike the PDP, and is built from the same pinned OpenFTV commit (CI checks the two Dockerfiles and `go.mod` agree).
  - The Manager's PAP is constructed without a file store (`apps/manager/server/pap.go`), so policies can only arrive over the API. `scripts/seed-openftv-manager.py` pushes `policies/` in — the same path the management interface uses — with ids derived as uuid5 of the repo-relative path, so re-runs update in place. Git stays the source of truth; the Manager is the distribution mechanism.
  - Policies that have left git are *retired* (the bundle's tag is stripped, so `eam/bundles/bundle.go` stops selecting them) rather than deleted, because `DELETE /v1/policy/:id` fails with a foreign-key violation on `policy_audit` upstream. This is not cosmetic: the store is cumulative, and two policies declaring the same Rego `package` make the PDP fail to compile the whole set, so every request returns 500 until one is retired.
  - Adopting the Manager does **not** fix decision-log masking. Bundle-delivered policies reach the engine through the same `UpsertPolicy` path as file-delivered ones (`eam/pdp/controller/bundle.go` → `PAP.ReplaceAll` → the PDP's event sink), never through OPA's bundle plugin, so `data.system.log.mask` never resolves either way.
- **Akte van overlijden — a second bron and a second EUDI attestation.** New source service `brp-graphql-server` serving the BRP bronprofiel ([gbo-semantiek v0.3 `brp.graphql`](https://github.com/ICTU/gbo-semantiek/blob/main/v0.3/graphql/brp.graphql)): `IngeschrevenPersoon`/`Ingezetene`/`NietIngezetene`, nationaliteit, huwelijk, verblijfstitel, gezagsverhouding, immigratie and the binnen-/buitenlandse verblijfadres. A nabestaande discloses her PID and receives an `nl.gbo.brp.akte-van-overlijden` credential with her deceased partner's overlijdensgegevens; the query is rooted at her own persoonslijst and reaches the overledene only through `heeftHuwelijk.partners`, which is the authorization argument the policy mirrors. Mock data holds exactly one person who satisfies that shape (Frouke Jansen, BSN `999991772`, the PID-preprod persona); the other personen are married to a living partner, unmarried, or divorced.
  - Registered as its own FSC service `brp` (outway path `/brp`) behind the same provider peer as the BD bron, with its own `brp-sidecar` instance. `seed-bri-contract.sh` is now parameterised by `SERVICE_NAME`/`SERVICE_ENDPOINT_URL`/`GRANT_LINK_PATH`; `make fsc-seed-brp` seeds the new service.
  - New policy rule `EUD0002` with scope `brp:akte:overlijden`. Its `covers_fields` are disjoint from `EUD0001`'s, so a BD scope cannot open the BRP path and vice versa; the BD path's per-year axis is declared off.
  - The PDP selects the mirror schema per flow (`flowSchemaFiles`): `eudi:attestation` → BD, `eudi:attestation:brp` → BRP. Both bronprofielen expose `Query.ingeschrevenPersoon(bsn)` with a different `IngeschrevenPersoon`, so the flow name has to carry the bronprofiel.
  - The eudi-adapter dispatches on a per-usecase `bron` (`bd`/`brp`), which drives both the GraphQL query it builds and the wallet-attribute mapping.
  - The credential carries what a Dutch akte van overlijden carries and nothing more: the overledene (naam, geboortedatum/-plaats/-land, geslacht), the overlijden (datum, plaats, land), the ouders, the echtgenoot or geregistreerd partner, and the verklaring. The query fetches more — `datumVoltrekking`/`plaatsVoltrekking`/`landVoltrekking`/`datumOntbinding`/`redenOntbinding` select the right marriage and establish that it ended in death — but those belong on the huwelijksakte and are dropped, as are the BSN and the persoonslijst-ids. Three fields a paper akte does carry are absent because the bronprofiel has no equivalent: gemeente van opmaak + aktenummer, the aangever, and the tijdstip van overlijden.
- Repository governance files (`CODE_OF_CONDUCT.md`, `publiccode.yml`, `CHANGELOG.md`) and a `.github/workflows/codeql-analysis.yml` workflow to comply with the [ICTU GitHub policy](https://github.com/ictu/github-policy).
- Repository-owner section in `README.md`.

### Changed
- **Policy engine substituted: bare OPA → OpenFTV PDP (embedded OPA/Rego), with FSC-Inway connected directly.** The custom `pdp-service` (XACML context-handler) is retired: its two jobs moved into the OpenFTV PDP image. A GraphQL request-mapper (`services/openftv-pdp/mapper`, registered as `graphqltocontext`) walks the query and enriches the AuthZEN context with `resolved`, `resource`, `flow`, `trace_id` (Fsc-Transaction-Id) and — for EUDI — `pip.pid.pi`, resolved through BSNk so the engine and its decision log never hold a BSN. Policies use the OpenFTV contract (`package authz` → `allow`/`reason`); the deny reason reaches the consumer via `reasonUser.en`. The dev-portal reads decisions from the OpenFTV decision log in Loki (normalised to the legacy popover shape) and policy sources from disk; `/explain?mode=full|fails` is dropped (no OpenFTV explain API). `bd-inway` points at `https://openftv-pdp:8443/authzen/v1` with the existing self-signed CA. Note `PDP_POLICIES_LANGUAGE=rego`: the documented value `OPA` makes OpenFTV silently skip all policy files (reported upstream).
- **nl-wallet bumped v0.4.1 → v0.5.0 (`vendor/nl-wallet`), a lockstep migration.** v0.5.0 implements OpenID4VP 1.0's `client_id` rules: the loose `client_id_scheme` request field is gone and the `x509_san_dns:` prefix is mandatory, so a v0.4.1 wallet app and a v0.5.0 issuance-server cannot complete a session with each other in either direction. The pin comment claiming the preprod app *rejects* the prefixed `client_id` is retired with it.
  - The `client_id` is no longer configured, it is derived, and **`EUDI_CLIENT_ID` is gone**. v0.5.0 builds it from the issuance-server's own `public_url` (`x509_san_dns:<host>`, `client_id_from_public_url`) and the wallet requires the `client_id` in the universal link to be byte-for-byte identical. The server can produce no other value — additional SANs on the reader certificate are never used as the `client_id` — so an override could only ever hold a value that breaks the session. The landing page and the developer portal derive it from `EUDI_PUBLIC_URL` instead, and the variable is removed from compose, both frontends' runtime config, `.env.example` and `OBSERVABILITY.md`.
  - **`EUDI_READER_ORIGIN_URL` is gone** too. It only ever fed `requestOriginBaseUrl` in `reader_auth.json`, which no live server code and no TOML key reads — its single real consumer is the certificate mint step, where the wallet compares the value against the origin it actually reached, so it can only be the public URL. Having it separately configurable bought nothing and, in at least one working `.env`, held a stale value that no deployed certificate carried. The `reader_auth` templates now follow `EUDI_PUBLIC_URL` directly.
  - The `EUDI_PUBLIC_URL` host became part of the crypto. v0.5.0 validates on startup that every reader certificate in `[disclosure_settings.*]` carries that host as a DNS SAN, so a tunnel hostname change is now a certificate change: both `EUDI_READER_CERT` and `EUDI_BRP_READER_CERT` have to be re-minted for the host actually served. Only the leaf moves — the CA the wallet trusts stays the same and carries no name constraints, so any hostname works under it. The `requestOriginBaseUrl` embedded alongside it is a separate check, and not merely displayed: the wallet compares it with the origin it actually reached, and a mismatch aborts the session *after* the certificate itself has validated — surfacing as a CANCELLED session with no error text rather than as the certificate problem it resembles.
  - `scripts/mint-brp-certs.py` → `scripts/mint-eudi-certs.py`, which now mints all five leaf pairs instead of one: both readers from a single `--public-url` (they always change together under v0.5.0), and both issuers plus the status certificate from a single `--issuer-host`, which makes the shared-subject rule the issuance-server enforces hold by construction rather than by a cross-check. `--only readers` covers the common case of a deployment hostname change. It verifies both invariants against the certificates it just produced, writes env-var lines to stdout and a summary to stderr, and never touches the CAs — those stay fixed, since they are what the wallet trusts.
  - PID and address merged into one `urn:eudi:pid:nl:1` credential upstream, and DigiD app2app was removed. Neither reaches this repo: every reader-auth config discloses only `bsn` from `urn:eudi:pid:nl:1`, and the demo does not use app2app.
- **Consent is retrieved by the policy, not by the request-mapper.** `policies/dvtp/gbo/consent.rego` queries the consent-register with `http.send` during evaluation, which is where the FTV standard puts attribute retrieval — and it makes a revoke effective on the next request. OpenFTV's own PIP cannot hold consent: its network PIP is a scheduled loader, and the PDP's attribute store rejects every update after the first create (its in-memory CAS byte-compares `marshal(unmarshal(v))` against the stored bytes), so it can carry no attribute that changes. An earlier note in this changelog said "PIP push is broken upstream" — more precisely, the defect is in the in-memory store, and the standalone `apps/pip` does have a Postgres backend; the PDP simply cannot be pointed at it, since `eam/config/pip.go` exposes only a file store and pull-configs. Lookups fail closed to `CONSENT_NOT_FOUND`.
- **The GraphQL schema travels with the policies.** The mapper builds its field→type map from the SDLs under the policy directory (`GBO_SCHEMA_DIR`, default `/policies`) instead of a generated `field-map.json` baked into the image, so `scripts/gen-field-map.sh`, its Go generator and the CI freshness check are gone. Type-qualified coverage keys need schema knowledge — the type graph is cyclic (`NatuurlijkPersoon.heeftOuder` → `NatuurlijkPersoon`), so a path-based key would need an infinite family of paths — but that knowledge is part of the catalogue and belongs with the policies the PAP manages, where it also hot-reloads. It is deliberately not fetched by introspection: that would make the source the authority on its own type graph, and relabelling a field's parent type would silently widen the coverage a rule grants.
- **The flow comes only from the signed FSC additional-claim.** `X-GBO-Flow` is gone from the eudi-adapter and from the mapper: it let a caller name the authorization regime it wanted to be judged under, while the trusted value was already in the token (`additional-claims-service` derives it from the grant, the provider's FSC-Manager signs it). A missing claim no longer defaults to `dvtp:query` — that silently selected the consent-based rules for a request that had said nothing — and instead matches no rule's dispatch, so the closed-world engine denies.
- **The mapper is built and tested like the rest of the repo.** `services/openftv-pdp` is a Go module pinned to the same OpenFTV commit the image builds from, with unit tests over the query walk (aliases, fragments, cycles, the depth cap, argument flattening, body decoding) and a CI job; a check keeps the module pin and `OPENFTV_REF` in lockstep. The `known` field is dropped from the resolved shape and from `engine.rego`: with no SDL behind it, it was a constant `true` sitting in a security predicate. The mapper now honours `operationName` — it walked the first operation while the source executes the named one — and a document with several operations and no name is `coverage_unverifiable`. Each `sed` in the Dockerfile asserts it changed something, since `sed -i` exits 0 on no match and would otherwise yield a PDP where the mapper is never registered and every policy evaluates an empty context. `openftv-pdp` and `dev-portal-backend` now build at PR time.
- GraphQL-playground moved from the bron to the developer-portal, and now covers every bron. `http://localhost:9003/playground` serves GraphiQL 5 + explorer + Voyager with a bron-keuze (`?bron=bd`, `?bron=brp`), each bron opening on its own example query — the akte-van-overlijden path for the BRP. Both tabs reach the bron over the portal's own origin (`/bron-api/<bron>/graphql`, proxied by nginx and by the dev-server), so no bron-port has to be published and the bron-servers need no CORS. The BRON-block in the strip links to the playground of the bron that run actually used. The tools are npm-dependencies now, so the ~90 lines of pinned CDN references and SRI hashes that the old page carried are gone with it — as is the page itself: `graphql-server` no longer serves `/playground` (a browser on `/graphql` gets GraphQL, not a redirect), and `brp-graphql-server` stops serving the GraphiQL 0.11 bundled with graphql-go/handler. `GRAPHQL_PUBLIC_URL` is retired: the playground is same-origin with the portal. Adding a third bronprofiel means one entry in `developer-portal/src/data/bronnen.ts` and one proxy route — no second page and no second set of pinned assets.
- Developer-portal architecture strip follows the bron of the run it shows. The EUDI chain's last two nodes are no longer fixed to the BD pair: an akte-van-overlijden run lights up `brp-sidecar`/`brp-graphql-server` and labels them as the BRP pair, where before both spans fell through unmapped and the nodes stayed grey — reading as "not reached" while the run had in fact reached them. Which bron a run used comes from the run itself (`gbo.bron` on the eudi-adapter span, plus the bron-services in the trace), so the portal holds no usecase → bron table beside the adapter's catalog; a third bronprofiel adds its service names in `developer-portal/src/data/bronnen.ts` and nowhere else. The bron-sidecar image now takes its log- and span-identity from `OTEL_SERVICE_NAME`, so the `brp-sidecar` instance no longer reports itself as `bron-sidecar`.
- Bron playground replaced: `graphql-server` now serves its own page on `/playground` (GraphiQL 5 with the explorer plugin for click-together queries, plus a Schema tab rendering the type graph with GraphQL Voyager) instead of the retired GraphQL Playground bundled with `graphql-go/handler`. Assets are pinned per version and SRI-checked; `/graphql` in a browser redirects to `/playground`, while `POST /graphql` and `GET /graphql?raw` are untouched.
- `SECURITY.md` restructured with explicit *Current status*, *Supported versions*, and *Reporting a vulnerability* sections.
- Bron GraphQL-schema switched from the custom `inkomensgegevens` shape to the BD bronprofiel schema ([gbo-semantiek v0.3 `bd.graphql`](https://github.com/ICTU/gbo-semantiek/blob/main/v0.3/graphql/bd.graphql)): queries now go via `ingeschrevenPersoon(bsn)` → `heeftBelastingjaarAangifte` → `AangifteIH` with `Bedrag` amounts. EUDI inkomensverklaring metadata updated accordingly (`peil_datum`/`grondslag_*`/`status_code` out, `indieningsdatum`/`status` in).

### Added
- Per-year policy enforcement: `heeftBelastingjaarAangifte` accepts a `belastingjaren` filter (demo-bron extension of the upstream schema) so the PDP can see the requested years. New `years_in_scopes` rule axis requires every requested belastingjaar to be covered by a `bd:ib:<year>` scope in the consent (DVT0001) or the rule's `allowed_scopes` (EUD0001) — a query for a year the citizen did not consent to fails with `YEAR_NOT_COVERED`; a missing year filter fails closed.
- Flow dispatch in the GBO rule-engine: consent-based rules (DVT0001) only fire when `pip.consent` is present, PID-based rules (EUD0001) only when `pip.pid` is present, so deny reasons come from the flow's own rule (implements the dispatch the rule files already documented).
- PDP by-PI consent lookup now unions all ACTIVE consents for the PI (per-year scopes may live in separate records; broadening consent over time works).
- Compose host ports are configurable via `GBO_PORT_*` env vars (defaults unchanged), so two worktree stacks can run side by side.
- DvTP requests now carry the referenced consent (`X-GBO-Consent-Id` header through the FSC path); the PDP's PIP lookup evaluates exactly that record (the by-PI union is only a legacy fallback), so revoking a consent deterministically denies queries backed by it and sibling consents for the same PI no longer rescue a query.
- fsc-infra is deployable per worktree: `FSC_PROJECT_NAME` + `FSC_PORT_*` in `fsc-infra/.env` (project name, network, host ports) and `FSC_INFRA_NETWORK` in the root `.env` let multiple checkouts run isolated FSC instances side by side.
- Dev-portal scenario `use-jaar-niet-geconsenteerd-deny` demonstrating per-year consent.
- Demo policies (Rego) and GraphQL mirror-schemas are now baked into the `opa` and `pdp-service` images (`services/opa/Dockerfile`, `services/pdp-service/Dockerfile`, build context = repo root). The compose stack and the Helm example values no longer mount them; a volume mount at `/policies` or `/schemas` still shadows the baked-in files if present.
- DvTP browser flow: the dienstverlener-backend intersects requested belastingjaren with the consent's scopes and only queries consented years; unconsented years are returned as `denied_years` and rendered greyed out in the dienstverlener-mock result page instead of failing the whole query.
- Landing page (`landing-page`, :9000): a public front door for the demo that explains what GBO is and sketches the three flows (DvTP, EUDI, OOTS) over the shared pipeline. "Zelf uitproberen" offers exactly the two flows that are live — start the DvTP flow at HypotheekBV (with the consent portal named as its second step rather than as a separate entry point), or scan a wallet QR rendered on the page itself. That QR is assembled client-side from `EUDI_PUBLIC_URL` + usecase + `client_id`, the same universal link the developer portal builds; the wallet opens the session against the issuance-server on scan, so the page needs no backend. Without `EUDI_PUBLIC_URL` it explains why there is nothing to scan instead of showing a dead QR. The developer portal is presented separately as an inspection console to open *after* a flow, not as a third thing to try. Every outbound link is resolved at runtime (`VITE_*` on the dev-server, `runtime-config.js` via envsubst in the nginx image) so the same image serves both the local stack and a deployed environment.
- Bron GraphQL playground: `graphql-server` now serves the GraphQL Playground bundled with `graphql-go/handler` (dark, with a Docs + Schema explorer) on a browser `GET /graphql` instead of GraphiQL 0.11, and the developer portal's BRON block deep-links to it via `GRAPHQL_PUBLIC_URL` with a query prefilled through the `query` URL param. `POST /graphql` and `?raw` still return GraphQL results. Introspection was already enabled — graphql-go answers `__schema`/`__type` unconditionally — and is now covered by a test. The playground reaches the bron directly, so it bypasses FSC-Inway, the sidecar, the PEP and the PDP: no consent check, no BSN pseudonymisation, as the prefilled query's leading comment states.
